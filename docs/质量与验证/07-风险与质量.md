## 2. 质量属性落实

- **正确性**：文件内容和命令结果来自本地工具，完成摘要引用实际验证。
- **安全性**：Renderer 沙箱、IPC 白名单、项目路径边界、审批、超时、密钥存储和命令环境隔离。
- **可恢复性**：工具失败反馈模型；任务失败不自动提交、不回滚用户文件；重启后遗留运行记录显示为意外中断。
- **可解释性**：时间线展示工具、目标、结果，并拆分批准等待与执行耗时；Diff 展示实际变化。
- **可维护性**：模型、循环、工具、桌面服务和 UI 使用明确接口。
- **可移植性**：核心 Agent 不导入 Electron，可在单元测试中独立运行。

## 3. 代码质量门禁

- TypeScript strict 模式，无类型错误。
- 核心安全逻辑和失败路径必须有自动化测试。
- Renderer 不启用 Node 集成，不拼接模型生成的 HTML。
- 外部进程必须有批准、超时、整棵进程树取消、退出码和截断处理。
- 文件扫描跳过依赖、缓存、构建目录和符号链接。
- 新增或变更需求同步更新追踪矩阵、测试和日志。

## 4. 提交与材料合规

- 公开 Git 仓库在题目发布后创建，保留完整真实历史。
- 不改写已推送提交，不伪造开发过程。
- 截止后不向远端推送新提交。
- `README.txt` 不超过 1000 汉字，包含 URL、运行方法和特色。
- MP4 不超过 2 分钟和 200 MB，不出现 Key、用户名或无关个人文件。
- 最终压缩包只放要求的材料，并按题目命名。

## 5. 里程碑评审清单

1. 本轮实现对应哪些需求和用例？
2. 哪些结论有测试、窗口检查或真实命令证据？
3. 哪些行为仍未验证，是否在文档中明确？
4. 新增了什么权限或数据边界？
5. 面试时能否从源码指出自研 Agent 与 Electron UI 的分界？

## 6. 软件质量管理职责

这是单人项目，但产品、设计、开发、测试和发布职责在过程上必须分离：需求阶段先写验收标准，编码阶段按设计接口实现，验证阶段从失败路径和交付约束重新检查，不能用开发者直觉替代证据。最终范围、风险接受和发布冻结由项目负责人决定；模型服务只是运行依赖，不是质量责任主体。

| 质量活动 | 责任 | 产出 |
| --- | --- | --- |
| 需求/用例评审 | 项目负责人 | 范围、优先级、可测试验收标准 |
| 架构与安全评审 | 设计/开发角色 | 信任边界、ADR、影响模块 |
| 代码与测试 | 开发角色 | 实现、相关测试、完整门禁 |
| 系统验收 | 测试角色 | 自动化、桌面和真实模型证据 |
| 发布评审 | 发布角色 | 凭据、视频、README、Git 和压缩包复核 |

## 7. 度量、缺陷与质量审计

当前使用少量可解释指标：135/135 自动化测试通过、28/28 个 FR 具有追踪映射、类型检查与构建通过、真实修改闭环三次成功。它们分别代表当前回归、追踪、构建和真实模型证据，不混同为代码覆盖率或服务可用率。计划模式的自动化状态机证据已完成，真实模型桌面复验仍单独列为人工证据，不用单测数字替代。

缺陷按 Blocker、P0、P1、P2 管理，状态为“发现—可复现—已定位—已修复—已复测—关闭/延期”。Blocker/P0 阻止候选发布；P1 必须在冻结前修复或明确降级；P2 可进入路线图。质量审计至少检查需求追踪、IPC/权限变化、关键失败测试、凭据形态、文档链接、演示基线和未验证声明。

完整质量目标、效能指标、阶段门禁和缺陷定义见 [16-中期生命周期基线.md](../历史归档/16-中期生命周期基线.md)。
