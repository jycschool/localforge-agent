# 两分钟演示视频脚本

## 1. 成片策略与硬约束

两分钟内不现场等待模型。正式录制采用“**先完整运行，后读取同一条真实历史**”的方式：录制前完成一次 2/6 → 修改 → 6/6 的真实任务并保留历史、命令输出、成果卡和 Diff；录制时只打开这条已完成记录进行讲解和无副作用回放，不再次请求模型或执行命令。

这不是预制假数据，也不是把不同任务拼接在一起。成片应主动说明“下面展示的是我录制前完整跑好的同一条真实任务记录”，所有失败、修改、成功、退出码和 Token 必须来自同一个历史 id。

建议成片 1 分 45 秒至 1 分 58 秒，导出 H.264 MP4、1080p、30 fps、4—6 Mbps且小于 200 MB。画面不得出现 API Key、Token 明文、系统用户名、个人目录前缀、无关通知或其他聊天。

正式任务使用 `demo/order-pricing`。其固定 6 项验收测试初始为 2 项通过、4 项失败，修复后为 6 项通过。完整彩排和备用演示见 [25-全功能演示操作手册.md](25-全功能演示操作手册.md)。

## 2. 录制前先跑好一条成功记录

### 2.1 恢复和复核基线

1. 把演示目录恢复到已提交状态，确认 `src/shipping.mjs` 仍使用错误的 `>` 边界且没有输入校验。
2. 进入演示目录运行 `pnpm test`，必须看到 `tests 6`、`pass 2`、`fail 4`。
3. 在仓库根目录运行 `pnpm run verify:delivery`，确认演示故障基线、README、文档链接和凭据扫描全部通过。

### 2.2 在 RepoForge 中预运行

1. 使用桌面 `RepoForge 代码锻造` 快捷方式或 `release/RepoForge-win32-x64/RepoForge.exe` 启动最新构建，不在成片中展示命令行启动过程。
2. 只打开 `demo/order-pricing`；模型选择已通过“文本、流式、Usage、工具调用”自检的配置。
3. 权限选择“工作区”，执行模式选择“先规划”，最大步骤建议 20；选择 `Test-first demo verification` Skill。
4. 新建会话，清除旧附件和任务草稿，发送下方主任务。
5. 正常审核计划，批准首测和复测。必须真实看到首测 2/6、只修改 `src/shipping.mjs`、复测 6/6 和退出码 0。
6. 任务结束后记住该条历史的时间与标题，确认成果卡、完整历史、命令输出和 Diff 都能重新打开。
7. **录制前不要恢复 Demo、不要删除这条历史、不要新跑第二条任务**。保持修复后的 6/6 文件状态，确保当前 Diff 与历史结果一致。

### 2.3 录屏画面准备

1. 将窗口设为 1920×1080 或 1600×900，系统缩放固定，双击各分隔条恢复默认布局。
2. 关闭微信、邮箱和系统通知；文件路径只显示项目内相对路径。
3. 打开历史窗口，预先定位刚才成功的记录并确认它显示工作区权限、计划模式、所选 Skill、两次测试和唯一变更文件。
4. 排练一遍“历史详情 → 首测命令卡 → 修改事件 → 复测命令卡 → 成果卡 → Diff”的点击顺序，全程不需要网络。

## 3. 预运行时使用的任务

```text
修复 calculateShippingFee：普通会员订单满 99 元免邮，高级会员满 59 元免邮；subtotal 必须是非负有限数字，membership 只能是 standard 或 premium。不要修改、删除、跳过或削弱现有测试。先运行现有测试取得失败基线，只修改实现，再运行同一测试验证。完成前说明实际测试结果和剩余风险。
```

## 4. 最终分镜与逐动作台词

### 4.1 开拍前摆好界面

正式录制直接从已经完成的成功任务开始，不拍桌面、不重新发送任务，也不现场打开设置：

1. RepoForge 最大化，画面只包含应用窗口；关闭所有系统通知。
2. 当前项目必须是 `order-pricing`，右侧停在刚完成的修复会话底部，状态显示完成。
3. 左侧展开 `src`、`test` 和 `.localforge/skills`；“本次变更”只应有 `src/shipping.mjs`。
4. 中间代码区预先打开 `src/shipping.mjs`，底部“运行输出”保持可见，并让 `2/6 → 6/6 通过` 进度条完整露出。
5. 右侧停在当前真实成果卡：`1 个文件 +12/-3`、`6 项测试通过`、`12 次工具调用·2 次失败`、约 `64k Token`；已完成计划保持默认收起并显示 `4/4`。
6. 把鼠标停在窗口空白处后再开始录制。所有需要展示的数字至少停留 1.5 秒。

### 4.3 手机提词卡

下面十句与上表一一对应。排练时手机只看这一段；每换一句做一次对应动作：

1. 这是我独立实现的 RepoForge 代码锻造智能体。画面是录制前真实完成的修复结果，现在不再调用模型。
2. 左侧是项目与变更，中间是代码、Diff 和命令，右侧记录 Agent 全过程；还支持多模型、Skill、Memory、附件和历史。
3. 本次只改一个文件，增加十二行、删除三行，六项测试全通过；两次失败工具调用也被如实保留。
4. 任务使用计划模式，写入前人工批准；四步分别是首测、分析修改、复测和总结，现在全部完成。
5. 首次测试两项通过、四项失败；修改后同一命令六项全过。这些来自本地真实输出，不是模型声明。
6. 模型只改 shipping 实现，修正九十九元和五十九元免邮边界，并增加金额和会员类型校验。
7. 复测退出码为零；完成门禁同时要求计划收尾和验证证据，不能只说已经修好。
8. Diff 证明测试未改；前后快照可审查，恢复时还会检查内容冲突。
9. 历史可无副作用回放，不再调用模型或命令。这就是可审批、可验证、可恢复的 Agent 闭环。

### 4.4 超时或卡顿时怎么删

- 到 01:00 已经慢了 5 秒：第 6 句删去“读取源码和验收条件后”。
- 到 01:30 已经慢了 8 秒：第 8 句只说“成果卡由真实事件、命令输出和文件快照自动汇总”。
- 不论多赶，都不能删掉 `2/6`、`6/6`、唯一实现修改和 Diff 四个证据镜头。
- 鼠标点错后不要在画面里来回寻找；停止录制，回到开拍前状态重新开始。

## 5. 剪辑与真实性规则

- 可以剪掉程序启动空白和窗口切换，但不改变同一历史中的事件顺序。
- 不展示模型等待动画，不在录制期间重新发送任务，不需要等待远端服务。
- 首测 `2/6`、文件修改、复测 `6/6`、成果卡和 Diff 必须来自同一个历史 id。
- 不把失败轮和另一条成功轮拼在一起；预运行失败就恢复 Demo 后整轮重跑。
- 关键退出码、`2/6`、`6/6` 和 Diff 至少各停留 1.5 秒。
- 若预运行没有使用 `edit_file_lines`，不要补录或声称使用；统一说“精确修改受旧内容或摘要保护”。
- 可在台词或字幕标注“录制前真实运行结果 / 本地历史回放”，避免观众误以为正在实时请求模型。

## 6. 预运行异常处理

| 异常 | 处理 |
| --- | --- |
| 基线不是 2/6 | 恢复 Demo 后重新运行，不修改测试数量或台词 |
| 收到 401 | 在录制外重新保存 Key 并完成模型自检，任何画面都不得保留 Key |
| 收到 429 | 该轮作为失败历史保留但不用于正式视频；稍后从 2/6 基线重新跑完整成功轮 |
| 模型工具调用协议失败 | 保存失败历史供排查，切换到通过工具自检的配置后整轮重跑 |
| 命令误点拒绝 | 可以作为答辩安全证据，但正式成功轮从干净基线重新开始 |
| 达到步骤上限 | 检查最后动作，缩小任务或切换模型；不要把硬上限无限调高 |
| 测试被修改 | 立即恢复 Demo；确认计划和 Skill 均限制只改 `src/shipping.mjs` |
| 录制时历史或 Diff 不一致 | 停止录制，回到预运行记录核对；不要用另一条历史补画面 |

## 7. 成片验收清单

- [ ] 总时长小于 2:00，MP4 小于 200 MB，可从头播放到结尾。
- [ ] 明确说明这是录制前完整跑好的同一条真实历史，不冒充实时模型响应。
- [ ] 历史中的初始基线为 6 项测试、2 项通过、4 项失败。
- [ ] 展示工作区权限、计划模式、所选 Skill 或历史上下文清单。
- [ ] 保留首测失败、唯一实现修改、同一测试 6/6 成功的事件顺序。
- [ ] 出现真实退出码、成果卡、变更列表、Diff 和历史/回放。
- [ ] 台词准确区分模型 tool call、本地工具执行和本地历史读取。
- [ ] 不出现 Key、Token 明文、用户名、个人目录、无关聊天、邮箱或通知。
- [ ] 视频中的测试数、退出码、步骤和最终摘要与同一条历史记录一致。
- [ ] 录制完成后恢复 Demo，并重新确认 2/6 基线。
- [ ] 使用 `pnpm run package:delivery -- -StudentName "姓名" -VideoPath "视频绝对路径.mp4"` 生成最终 zip，并确认其中只有 `README.txt` 与 `demo.mp4`。

## 8. 录制完成后的恢复

1. 关闭录屏，保留原始视频备份。
2. 在 RepoForge 的“本次变更”中恢复全部；若内容摘要冲突，先备份再人工恢复，不强制覆盖。
3. 进入演示目录运行 `pnpm test`，确认重新回到 `pass 2`、`fail 4`。
4. 不必删除用于答辩的成功历史；历史是本机证据，不进入 Git，也不再次调用模型。

## 9. 30 秒架构备用说明

“系统分为四层：Renderer 负责可观察界面；Preload 只暴露白名单 IPC；主进程管理项目、审批、密钥和历史；核心 AgentLoop 通过 ModelClient 调用模型，再把 tool calls 交给 ToolRegistry。模型没有直接文件权限，所有读写经过工作区边界，命令逐次审批。工具业务错误带错误码和恢复建议并回传模型；重复无进展会先纠偏再熔断。终止条件包括有效最终文本、用户取消、步骤上限、重复失败和不可恢复的请求或协议错误。”
