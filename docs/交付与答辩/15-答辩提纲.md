# 答辩问题与源码带看提纲

## 1. 30 秒项目说明

RepoForge 是一个独立 Electron 桌面 coding agent。Electron 只负责窗口、IPC 和系统安全能力；真正的 Agent 由仓库内的 ModelClient、AgentLoop、ToolRegistry 和 WorkspaceTools 组成。模型每轮只能返回文本或原生 tool call，本地工具完成项目内的读取、精确修改和命令执行，再把结构化结果放回消息历史。终止条件包括最终文本、最大步骤、用户取消和不可恢复错误。命令逐次审批，路径限制在用户打开的项目，所有变化都能从时间线、真实退出码、历史和 Diff 复核。

## 2. 最可能的追问

### Q1：为什么这不是普通聊天界面，而是 Agent？

聊天模型只生成文本；RepoForge 会把工具 schema 交给模型，解析 tool call，在本地执行后把结果按同一个 `tool_call_id` 回填，再让模型依据真实结果决定下一步。这个“观察—行动—反馈—继续/终止”的多轮闭环在 `agent/agentLoop.ts` 中自行实现。

### Q2：Electron 会不会也算借用了现成 Agent？

不会。Electron 只提供桌面窗口、进程和 IPC，不提供模型决策、消息循环、工具调用、代码理解或任务规划。删除 Renderer 后，核心 Agent 接口和测试仍能运行；删除 AgentLoop 后，Electron 本身无法完成任何编程任务。

### Q3：为什么不用 VS Code 扩展？

最初做过 VS Code 形态评估，但答辩时文件树、Diff 和命令能力容易与编辑器已有能力混淆。后来保留核心 Agent，改为独立 Electron 工作台，使“展示层”和“自行实现的 Agent 能力”边界更清楚。真实决策过程保存在 ADR-0001 与 ADR-0002，没有覆盖历史。

### Q4：为什么不用 Agent 框架或 SDK？

题目要求重要逻辑自行实现。项目直接通过 HTTP 调用 OpenAI-compatible `chat/completions`，自行维护消息数组、tool schema、调用分发、终止和错误状态。依赖清单只有 Electron、TypeScript、构建和测试工具，没有 LangChain、AutoGen、OpenAI Agents SDK 等框架。

### Q5：一轮消息具体包含什么？

初始消息是 system prompt 和用户任务。模型若返回 tool call，assistant 消息原样进入历史；每个本地结果再作为 `role=tool`、带对应 `tool_call_id` 的消息追加。下一次请求携带此前所有消息和同一组工具定义，因此模型能看到真实文件内容、失败测试和拒绝结果。

### Q6：上下文是怎样组织的？

固定系统规则先写入安全边界，再加入用户本次启用的项目 Memory 和勾选的 Skill，最后是任务文本及可选的当前文件路径。Memory 内容可以保存但停用；选中文件只提供路径，不把 Renderer 中的任意内容直接信任为源码，模型必须调用读取工具获取当前内容。

### Q7：Memory 和对话历史有什么区别？

对话历史是一次任务内的逐轮消息，用于保持 tool call 因果关系；任务历史是本机可回看的受限记录；Memory 是用户显式维护、跨任务使用的项目约定。Memory 不由模型自动写入，并明确标记为可能过期，必须用当前文件核实。

### Q8：Skill 是不是动态插件？

不是。Skill 只是项目 `.localforge/skills` 中用户选择的 Markdown 工作说明，不加载代码、不注册新工具，也不能覆盖路径、审批和系统安全规则。主进程在任务开始时按 id 重新扫描文件，Renderer 不能注入任意 Skill 正文。

### Q9：模型输出怎样解析？

ModelClient 先检查 HTTP 与 JSON，再严格校验顶层对象、非空 choices、assistant message、文本分段和 tool call。每个调用必须是 function 类型，具有非空且不重复的 id、合法工具名和编码为对象的 JSON 参数。损坏协议不能被静默丢弃，否则可能把坏调用误判为任务完成。

### Q10：为什么工具参数错误不直接终止，而协议错误要终止？

合法 tool call 中的路径缺失、旧文本不匹配或测试非零退出，是模型可以根据结构化结果修正的业务错误；消息本身缺少 call id 或参数不是 JSON 对象时，系统无法可靠配对后续结果，继续可能破坏对话因果关系，因此明确失败。可恢复错误若连续 3 次以相同工具、参数和结果重复，也会触发熔断，避免模型把全部步骤浪费在同一个错误上。真实演示中模型两次遇到精确替换失败，都通过重新读取恢复。

### Q11：文件操作如何防止越界？

相对路径先做词法范围检查，再对既有目标或最近既有父目录做 `realpath` 检查；符号链接不进入默认遍历。目录列表、搜索、读取、替换和写入都使用同一项目根边界。用户未打开的目录没有工具句柄。

### Q12：为什么使用精确替换而不是让模型随意覆盖？

精确替换要求旧文本恰好出现一次。0 次说明模型看到的内容过期或不准确，多次说明目标含糊，两种情况都不写入。模型可以重新读取后重试。它比整文件覆盖更容易审查，也能防止错误匹配悄悄改到别处。

### Q13：命令为什么必须逐次批准？

命令的副作用范围比文件工具大，单次允许不能推导出后续命令也被授权。审批框显示原因、完整命令和固定 cwd；拒绝时不创建进程，并把拒绝作为工具结果返回模型。批准等待和真实执行耗时分别记录，避免把人工等待误报为性能。

### Q14：停止和超时如何清理子进程？

AbortSignal 同时连接模型请求、AgentLoop 和本地命令。Windows 使用系统进程树终止，POSIX 使用独立进程组并提供强制终止兜底。自动化测试启动父子进程，超时后等待确认后代没有写出存活标记。

### Q15：循环有哪些终止条件？

1. assistant 返回有效文本且没有 tool call：完成；
2. assistant 既无文本也无 tool call：失败，不能用默认摘要伪报完成；
3. 达到最大步骤：失败并保留已有事件；
4. 用户停止：取消模型请求或命令并返回 cancelled；
5. 认证、最终限流、网络或协议错误：失败；
6. 工具业务错误：通常不终止，结果回传模型决定下一步；但连续 3 次完全相同的失败调用会提前失败并显示具体原因。

### Q16：429 为什么重试，为什么只重试两次？

429 与常见 5xx 可能是短暂服务波动，因此在单次模型调用内有限重试，优先遵守最大 15 秒的 `Retry-After`，没有提示时短指数退避。等待可取消，最多两次避免长时间占住任务或持续消耗配额。最终仍失败就明确显示“稍后重试或切换模型”，不伪造完成。

### Q17：怎么证明模型真的修复了问题？

演示项目的故障基线固定为 6 项测试中 2 项通过、4 项失败。真实模型共完成三轮修改闭环，步骤数为 10、10、9；三轮二次测试和 RepoForge 外独立复核都是 6/6。历史保存了模型回合、两次审批、退出码和唯一改动文件，Diff 保存任务前后的实际内容。

### Q18：有没有验证模型会遵守只读要求？

有。真实只读任务在 6 步、24 条事件内完成，只调用项目结构和读取工具，准确预测 4 项失败测试；没有选 Skill、没有运行命令、没有文件改动。历史详情显示 0 个改动文件。

### Q19：任务历史保存在哪里，会不会泄露 Key？

历史按项目真实路径摘要隔离，保存在 Electron `userData/run-history`，不写入 Git。每项目最多 50 次，每次事件和消息都有上限；API Key 从未进入 AgentEvent 或历史对象，assistant 私有 reasoning 在落盘前移除。Renderer 只能经 Preload 白名单读取。

### Q20：API Key 如何保存？

环境变量 `LOCALFORGE_API_KEY` 优先且不落盘；界面保存时使用 Electron `safeStorage` 加密。公开设置只返回是否存在和来源，不含明文。Key 与 API Base URL 绑定，切换服务后不会把旧服务 Key 发送到新地址。本地命令不会继承 Key、Token、Secret 等敏感环境变量，防止批准命令把凭据打印回 tool result；普通环境变量仍保留。

### Q21：为什么不自动提交 Git，撤销又如何保证安全？

题目关注 Agent 核心，不是 Git 客户端。自动提交会把模型行为升级为版本历史副作用，因此仍由用户审查后自行提交。撤销也不会自动发生：用户必须在 Diff 或变更区二次确认，主进程再比较任务结束时的内容摘要；若文件后来被编辑器或其他进程修改，就拒绝覆盖。这样提供恢复能力，又保留用户并行修改。

### Q22：当前最真实的限制是什么？

免费 ModelScope 服务可能限流；四次修改尝试中有一次在写入前收到 429，系统如实失败并保留历史。Preload 和主进程 IPC 的关键边界已有自动化证据，全新克隆也已通过安装、测试、构建和桌面启动；尚未完成最终视频录制，也未制作可分发安装包。界面提供受限文本编辑，但不是完整 IDE，也不包含多人协作、多 Agent、语言服务、调试器或 Git UI。

### Q23：切换模型时如何避免 Key 和任务状态混乱？

每个模型配置独立保存 API 地址、Model-Id、运行参数和绑定该地址的加密 Key，列表只暴露 Key 是否存在。切换只接受主进程已保存的配置 id，并从下一条任务生效；运行期间界面与主进程双重拒绝切换。任务启动时把实际配置名称、模型、权限和档位写入历史，因此之后切换不会改变旧任务证据。旧版单配置文件会自动迁移，不要求用户重新粘贴 Key。

## 3. 五分钟源码带看顺序

1. `src/core/protocol.ts`：消息、tool call、事件和执行上下文的最小协议。
2. `src/agent/agentLoop.ts`：消息历史、工具回填、步骤和五类终止路径。
3. `src/model/openAICompatibleClient.ts`：HTTP、严格协议解析和有限重试。
4. `src/tools/workspaceTools.ts`：路径边界、精确替换、命令审批与进程树清理。
5. `src/main.ts`：项目状态、Key、Skill/Memory、历史和桌面审批的编排。
6. `src/preload.ts`：Renderer 唯一可见的白名单方法。
7. `src/renderer/app.ts`：过程、退出码、Diff、历史与安全富文本展示。
8. `tests/` 与 `docs/质量与验证/14-真实模型验证.md`：自动化证据和真实模型证据的边界。

## 4. 答辩时避免的错误表述

- 不说“模型直接读取/执行了本地文件”；应说模型提出 tool call，本地工具执行。
- 不说“测试通过所以所有功能都正确”；应说明运行的是哪组测试和退出码。
- 不说“Memory 会自动学习”；当前由用户显式维护。
- 不说“429 已彻底解决”；有限重试只能缓解短暂波动，不能增加远端配额。
- 不说“完整 IDE”或“支持多人协作”；当前产品边界是可观察、可控的 Agent 工作台。
- 不展示或口述 API Key，不在视频中打开含明文凭据的界面。
