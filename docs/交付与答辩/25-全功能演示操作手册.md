# RepoForge 全功能演示操作手册

## 1. 手册用途

本手册把“演示什么、怎么操作、看到什么、失败后怎么恢复”放在同一处，供三种场景使用：

- **两分钟正式视频**：录制前先完整跑好一条真实成功记录，录制时只读取历史、成果和 Diff，不等待模型，严格按 [12-演示视频脚本.md](12-演示视频脚本.md) 计时。
- **答辩完整展示**：用 8—12 分钟补充模型配置、Skill、Memory、计划、权限、历史、Diff 和恢复能力。
- **录制前彩排**：逐项核对环境、故障基线、输出证据和清理状态，避免把旧修复结果带入下一轮。

正式视频不需要把所有按钮都点一遍，也不需要现场等待模型。评分价值最高的是同一次历史中可复核的“失败基线—本地修改—成功验证—Diff”因果链；其他功能作为答辩备用演示。

## 2. 演示材料与固定口径

### 2.1 使用对象

| 对象 | 位置或名称 | 用途 |
| --- | --- | --- |
| 桌面程序 | `RepoForge 代码锻造.lnk` 或 `release/RepoForge-win32-x64/RepoForge.exe` | 无命令行启动程序 |
| 演示项目 | `demo/order-pricing` | 制造稳定的真实修复任务 |
| 演示 Skill | `Test-first demo verification` | 强制先测、只改实现、复测和报告真实结果 |
| 被修复文件 | `src/shipping.mjs` | 唯一预期代码变更 |
| 不可修改文件 | `test/verify.mjs` | 6 项固定验收测试 |
| 测试命令 | `pnpm test` | 首次应为 2/6，修复后应为 6/6 |

### 2.2 固定故障基线

录制前进入 `demo/order-pricing` 执行 `pnpm test`，或在仓库根目录执行 `node --test demo/order-pricing/test/verify.mjs`。只有输出满足以下三项才开始录制：

- `tests 6`
- `pass 2`
- `fail 4`

若不是 2/6，先停止录制。不要临时改测试凑数字；应从 Git 恢复 `demo/order-pricing/src/shipping.mjs` 和 `demo/order-pricing/test/verify.mjs`，或在 RepoForge 的“本次变更”中使用“恢复全部”，再重新验证。

### 2.3 安全准备

1. 关闭聊天、邮件和系统通知，隐藏无关窗口与桌面个人文件。
2. 设置页只展示模型配置名称、状态和 Model-Id，不展开或粘贴 Token。
3. 打开项目时只选择 `demo/order-pricing`，不要把整个桌面或主仓库用于正式修复演示。
4. 权限选择“工作区”，运行模式选择“先规划”，最大步骤建议 20。
5. 点击模型“测试连接”，确认状态为已验证；遇到 401 先检查 Token 和账号绑定，遇到 429 稍后重试或切换可用配置。
6. **预运行前**新建会话并清空旧附件和本次变更；**正式录制前**则保留刚完成的成功历史与 Diff，不再发送任务。

## 3. 三条推荐演示路线

### 3.1 路线 A：两分钟正式视频

具体秒表和台词以 [12-演示视频脚本.md](12-演示视频脚本.md) 为准，分成“预运行”和“录制”两段：

1. **预运行（不录屏）**：恢复 2/6 基线，选择 `Test-first demo verification`、工作区权限和先规划，完整执行主任务。
2. **验收预运行**：确认同一条历史包含计划审批、首测 2/6、唯一实现修改、复测 6/6、退出码 0、成果卡和 Diff。
3. **保持现场**：不要恢复 Demo，不删除成功历史，不再发送任务；预先定位该条历史。
4. **正式录制**：从桌面图标与项目树开始，打开成功历史并口头说明“这是录制前刚完成的真实运行记录”。
5. **按顺序展示**：计划 → 首测 2/6 → 修改事件 → 复测 6/6 → 成果卡 → Diff → 无副作用回放。
6. **录制后清理**：恢复 Demo 并重新确认 2/6，为下一次彩排保留稳定基线。

### 3.2 路线 B：8—12 分钟答辩完整展示

在路线 A 前后增加以下内容：

1. **启动与布局（约 1 分钟）**：展示三栏结构、左右和上下分隔线、文件图标、快速打开与文件预览。
2. **模型与上下文（约 2 分钟）**：展示多模型配置切换、连接诊断、Skill 选择、Memory 启停、新建会话和附件清单。
3. **只读理解（约 1 分钟）**：执行只读任务，证明无命令、无写入时也能通过工具理解项目。
4. **计划与修复（约 4 分钟）**：答辩时间允许时可以现场完成 2/6 到 6/6；网络不稳定时也可使用正式视频保存的真实历史解释，明确不是实时运行。
5. **证据与恢复（约 2 分钟）**：展示命令卡、测试进展、Token、成果卡、Diff、历史回放和恢复全部。
6. **工程交付（约 1 分钟）**：展示 GitHub Actions 的质量门禁与 Windows x64 免安装制品，说明发布标签才触发 Release。

### 3.3 路线 C：异常与安全备用展示

这条路线不放进正式两分钟视频，答辩被追问时再演示：

- 拒绝一次命令：进程不启动，界面显示“未执行”，Agent 收到结构化拒绝结果。
- 输入越界路径：工具返回稳定错误码、是否可重试和恢复建议，不泄露项目外文件。
- 人工停止任务：模型请求或命令被取消，历史保留已发生事件。
- 手动编辑冲突：外部内容摘要变化时保存被拒绝，不覆盖新内容。
- 直接模式写入后不验证：完成门禁要求重新读取或运行相关命令，不能用一句“已完成”绕过。
- 重复相同失败或来回读取：先给恢复提示，持续无进展时提前终止，不机械耗尽 20 步。

## 4. 可直接复制的演示任务

### 4.1 主修复任务

```text
修复 calculateShippingFee：普通会员订单满 99 元免邮，高级会员满 59 元免邮；subtotal 必须是非负有限数字，membership 只能是 standard 或 premium。不要修改、删除、跳过或削弱现有测试。先运行现有测试取得失败基线，只修改实现，再运行同一测试验证。完成前说明实际测试结果和剩余风险。
```

建议配置：工作区权限、先规划、选择 `Test-first demo verification`。预期证据：计划获批后第一次测试 2/6，只修改 `src/shipping.mjs`，第二次测试 6/6，退出码 0。

### 4.2 只读理解任务

```text
只读检查这个项目：解释 calculateShippingFee 当前行为与 test/verify.mjs 需求之间的差异，并列出会失败的测试及原因。不要修改或创建任何文件，不要运行命令，只使用查看项目结构、搜索和读取工具。
```

建议配置：只读权限、直接执行、不选择 Skill。预期证据：0 个改动文件、0 条已执行命令，回答能解释 4 个失败点。

### 4.3 附件与连续追问任务

先把 `test/verify.mjs` 作为附件加入当前会话，再发送：

```text
根据附件中的验收条件，先说明最小修改范围和验证命令，不要立即修改文件。
```

回答后继续发送：

```text
保持刚才的范围，切换为先规划并提交可审核计划；不要扩大到测试文件。
```

预期证据：同一会话可上下滚动看到用户和 Agent 消息，第二问继承前文；发送清单准确列出附件、Skill、Memory、权限和运行模式。

## 6. 录制前主修复任务逐步操作

### 6.1 打开与配置

1. 启动 RepoForge，打开 `demo/order-pricing`。
2. 展开项目树，确认存在 `src/shipping.mjs`、`test/verify.mjs` 和演示 Skill。
3. 顶部选择已验证模型；权限选“工作区”；运行方式选“先规划”；最大步骤为 20。
4. 在 Skill 中勾选 `Test-first demo verification`。
5. 点击“新建会话”，确认附件为空、本次变更为空。

### 6.2 发送与批准计划

1. 粘贴主修复任务。
2. 打开发送清单，口头指出项目、模型、权限、模式、Skill 和附件；关闭后发送。
3. Agent 进行有限只读调查并提交计划。
4. 检查计划至少含“读取实现和测试、运行失败基线、只改实现、复测、总结证据”。
5. 若模型把“修改测试”写入计划，删除该步骤或退回计划；否则确认执行。

### 6.3 两次命令审批

1. 第一次出现 `pnpm test` 时，检查 cwd 位于演示项目、命令与原因合理后允许。
2. 保留首测 `2 passed / 4 failed` 和非零退出码画面；这不是 Agent 失败，而是预期故障基线。
3. 观察读取和编辑事件。若模型尝试模糊替换失败，让它按结构化提示重新读取，不要人工修改代码。
4. 第二次出现同一测试命令时再次允许。
5. 确认最终为 `6 passed / 0 failed`、退出码 0；计划全部完成后才出现最终答复。

### 6.4 审查结果

1. 查看成果卡，确认测试数、变更文件和命令数来自本次运行。
2. 打开“本次变更”，预期只有 `src/shipping.mjs`。
3. 打开 Diff，确认新增了阈值边界和参数校验，没有删除或跳过测试。
4. 打开历史详情并回放 5—10 秒，确认计划、工具、审批和结果顺序完整。
5. 若录制完成，恢复全部并重新运行基线测试，确保下一轮仍为 2/6。

## 7. 常见问题与恢复方法

| 现象 | 判断 | 处理 |
| --- | --- | --- |
| 首测不是 2/6 | Demo 未恢复或测试被改动 | 停止录制，恢复实现和测试，再在程序外复核基线 |
| 401 或提示绑定账号 | Token 无效、服务不匹配或 ModelScope 未绑定阿里云账号 | 在服务官网处理账号与 Token，再测试连接；不要录出 Token |
| 429 | 免费服务限流 | 等待后重试或切换已配置模型；如实保留失败历史 |
| 模型没有提出计划 | 运行方式选成直接执行，或模型未按协议调用计划工具 | 停止任务，新建会话，选择“先规划”后重发 |
| 计划确认卡显示不全 | 面板过窄或窗口过小 | 拉宽右栏、放大窗口；必要时滚动卡片，不缩放到不可读 |
| 精确替换/按行编辑失败 | 内容过期、旧文本不唯一或摘要不匹配 | 让 Agent 重新读取最新片段后缩小编辑范围，不手工伪造成功 |
| 达到步骤上限 | 模型重复调用、任务过大或远端能力不足 | 看最后三轮恢复提示；缩小任务或切换模型，不盲目增加上限 |
| 改了测试文件 | 违反演示约束 | 立即停止，恢复全部；确认 Skill 和计划都限制只改实现 |
| 历史切换后内容不变 | 当前运行未结束或选择的是同一会话 | 先停止/结束当前运行，再选择目标会话；必要时关闭重开历史窗口 |
| Token 显示异常 | 服务未返回 usage、流式聚合口径不同或旧历史缺字段 | 以历史中的实际 usage/估算标识为准，不把百分比当 Token 数 |
| 恢复按钮拒绝覆盖 | 文件在任务后又被人工或外部程序改动 | 先保存/备份外部内容，再人工处理冲突，禁止强制覆盖 |
| 视频超过两分钟 | 功能点过多或审批等待太长 | 正式视频只保留路线 A；Skill/Memory CRUD 等放到答辩备用演示 |

## 8. 录制完成后的清理

1. 在 RepoForge 中恢复本次代码变更，或从 Git 恢复演示实现与测试。
2. 再次运行演示测试，确认回到 2 通过、4 失败。
3. 删除彩排创建的临时 Memory、临时 Skill、附件和手动新建文件；仓库自带演示 Skill 保留。
4. 退出 RepoForge，确认没有残留测试进程。
5. 逐帧检查视频没有 Token、用户名、通知和无关桌面内容。
6. 检查 MP4 为 H.264、1080p、30 fps、时长小于两分钟、文件小于 200 MB。
7. 运行 `pnpm run verify:delivery`，再按交付清单打包。

## 9. 一页式口头操作摘要

正式视频只记住八句话：

1. 我打开的是仓库自带的固定故障 Demo，基线为 6 项中 2 项通过。
2. 我选择工作区权限、先规划和测试优先 Skill，发送清单把真实上下文展示给用户确认。
3. 计划批准前只能调查，用户可以改计划，批准后才开放当前权限允许的副作用工具。
4. 第一次测试由用户逐次批准，真实退出码证明当前有 4 项失败。
5. 模型通过本地工具读取并只修改实现；工具错误会带恢复建议回到同一消息循环。
6. 第二次批准同一测试后 6 项全部通过，完成门禁要求计划和验证证据都收尾。
7. 本次变更、命令卡、成果卡、历史和 Diff 来自同一次真实运行，不是静态演示数据。
8. 演示结束恢复 Demo 到 2/6，保证下一次彩排可以重复。
