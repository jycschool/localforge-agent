# 后续优化路线图

## 1. 目的

该路线图用于把“界面已经可用”推进到“核心 Agent 可证明、可恢复、可稳定演示”。优化顺序以课程考核价值、风险和 2026 年 9 月 2 日截止时间为依据，不以功能数量为目标。

当前基线已经包含独立 Electron 工作台、模型原生 tool calling、文件与命令工具、命令审批、空回复保护、可取消/可提前结束的文件遍历、1 MB 单文件边界、停止条件、变更审查、项目 Skill、项目 Memory、任务历史、严格模型协议解析、Windows 进程树清理、个人路径脱敏和 69 项自动化测试。Preload 与主进程 IPC 边界已经有自动化证据，后续重点转为视频彩排。

## 2. 优先级与验收标准

| 优先级 | 优化项 | 解决的问题 | 验收标准 |
| --- | --- | --- | --- |
| P0 | 任务历史与恢复 | 当前完整消息只存在于单次运行内，重启后无法回看 | 按项目列出最近任务；保存状态、摘要、步骤、时间线和消息；重启后可读取，不保存 API Key |
| P0 | 严格模型协议解析 | 损坏或不完整的 `tool_calls` 可能被过滤，存在误判完成风险 | 无效 JSON、空 choices、损坏调用、重复 call id 和非对象参数均产生明确协议错误；对应测试通过 |
| P0 | 真实模型端到端闭环 | 单元测试不能证明真实兼容模型能完成读、改、测 | ModelScope 完成一次只读任务和一次受控修改；真实测试失败能进入下一轮并被修复 |
| P0 | Windows 命令稳定性 | 超时和取消需要覆盖子进程、编码与残留进程 | 成功、非零退出、拒绝、超时、取消、中文输出均有测试或人工证据；取消后无遗留子进程 |
| P1 | 变更审查增强 | 当前 Diff 可读，但缺少单文件恢复和外部冲突提示 | 支持单文件恢复前确认；检测任务期间外部修改；Diff 明确新增、修改和统计 |
| P1 | Skill 图形化管理 | 当前只能通过项目文件创建和编辑 Skill | 在界面中新建、编辑和复制 Skill；删除操作单独确认；文件仍保存在 `.localforge/skills` |
| P1 | Memory 可观察性 | 用户无法直接确认本次实际注入的最终上下文 | 显示最后更新时间、字符数和本次注入预览；支持导入导出，不自动改写 |
| P1 | 代码浏览体验 | 只读预览缺少快速定位能力 | 增加行号、基础语法高亮、目录筛选和文件快速打开；大项目交互保持流畅 |
| P2 | 候选发布与启动验证 | IPC 边界已自动覆盖，最新开发候选和全新克隆均通过构建、启动；项目打开、预览与分栏烟雾检查完成 | 验证视频录制环境；按题目需要决定是否制作安装包 |
| P2 | 演示与交付固化 | 最终视频和材料仍需人工组织 | 演示项目、两分钟脚本、README.txt、凭据扫描和冻结清单全部完成 |

截至 2026-08-27，阶段 A 的任务历史、异常恢复映射、历史只读 IPC/界面和严格模型协议解析已完成；阶段 B 的命令稳定性已通过自动化验证，真实 ModelScope 模型累计完成三次“首测失败—修复—再测通过”闭环，后两轮验证了拆分后的命令计时。另一次尝试在修改前遇到 429，已经补入有限、可取消的重试。只读任务也以 0 命令、0 改动完成。Preload 映射与主进程 IPC 运行时校验已经纳入测试，最新开发候选和全新克隆均已完成构建、启动检查；下一步是视频计时与最终录制。

## 3. 实施顺序

### 阶段 A：状态与协议

1. 新增 `RunHistoryStore`，以项目真实路径摘要作为隔离键。
2. 在主进程记录任务开始、过程事件和最终状态。
3. 通过白名单 IPC 向 Renderer 暴露只读历史列表与详情。
4. 强化模型响应和 tool call 校验，禁止把损坏调用当作普通完成。

退出条件：任务重启后可回看；协议异常具有自动化测试和清晰错误文案。

### 阶段 B：真实执行稳定性

1. 使用已配置的 ModelScope 模型完成真实任务，并保留步骤、事件和独立复核记录。
2. 补命令退出、超时、取消和子进程清理测试。
3. 固化带首次失败的演示项目和任务描述。

当前进度：三次完整闭环分别为 10、10、9 步；基线 2/6，修复与外部独立复核均为 6/6。另一次因远端 429 在修改前失败并单独留证。阶段 B 的功能重复性退出条件已达成，远端配额仍作为发布风险保留。

### 阶段 C：审查与体验

1. 增强 Diff、恢复和冲突提示。
2. 增加 Skill 管理、Memory 注入预览和代码快速定位。
3. 完成桌面回归、打包与演示材料。

退出条件：功能、界面、文档和视频表述一致，没有无法解释的隐式行为。

## 4. 明确不扩展的范围

截止前不加入多人实时协作、多 Agent 编排、云端执行、完整 IDE、调试器、Git 客户端、向量数据库或模型自主记忆。这些能力会显著扩大服务端、安全和测试范围，不能提升当前核心闭环的可信度。

## 5. 提交与推送原则

- 按真实完成的里程碑提交：文档决策、核心实现、测试与验证分别形成可解释的提交。
- 不为了增加数量拆分无意义提交，也不把多个不相关功能压成一次提交。
- 不伪造提交日期、不改写已经推送的历史、不用空提交制造开发周期。
- 只有在类型检查、相关测试和构建通过后才推送；当天开发日志记录真实结果和剩余风险。

## 6. 总体验收

- 评审者可以从时间线、历史记录和 Diff 还原一次任务发生了什么。
- 模型不能绕过注册工具、项目路径边界和命令审批产生本地副作用。
- 错误、拒绝、取消和步骤耗尽都具有确定状态，不显示虚假成功。
- 自动化证据与真实模型演示共同覆盖核心闭环，文档不夸大测试范围。
