## 2. PDF 复核后发现的主要风险

### 2.1 “功能多”不是主要评分证据

原文允许功能很简单，面试重点是能否解释 Agent 为什么这样运转。因此截止前优先级应为真实多轮证据、失败路径和设计辩护，而不是增加完整编辑器、Git UI、多 Agent 或云服务。

### 2.2 视频必须证明真实编程过程

只展示漂亮界面或最终 Diff 不足。视频必须保留任务输入、工具读取、命令审批、失败测试、修改、再次测试和最终 Diff 的因果顺序。可以加速等待，但不能剪掉真实失败或把不同运行拼成虚假闭环。

### 2.3 提交历史本身是评审材料

评委会结合提交时间与内容了解开发过程。因此应按真实里程碑提交，减少无意义微提交，也不能人为改日期、压缩或改写已推送历史。推送频率可以按完整里程碑控制，但每个 commit 必须对应可解释成果。

### 2.4 凭据泄露是硬性违规风险

不仅仓库不能含 Key，README.txt 和视频也不能出现。发布前必须同时检查已跟踪文件、完整 Git 历史、构建产物、录屏画面和最终 zip；若曾误提交必须立即轮换，不能只删除当前文件。

## 3. 冻结前检查顺序

1. 在干净克隆中安装并运行 LocalForge，执行 `pnpm run verify` 与 `pnpm run verify:delivery`。
2. 使用最终 ModelScope 模型完成只读任务和演示修改任务。
3. 对演示任务连续彩排三次，记录成功率、步骤、命令和耗时。
4. 运行类型检查、118 项自动化测试和构建。
5. 匿名访问公开仓库，核对 README.txt 与提交历史。
6. 扫描当前树和 Git 历史中的凭据特征。
7. 录制并复看两分钟视频，确认没有 Key、用户名和无关通知。
8. 记录最终 commit，9 月 2 日 20:00 后冻结远端推送。
9. 使用 `package:delivery` 生成姓名 zip；脚本检查 MP4 签名、200 MB 上限、README 长度和压缩包内容，仍需人工确认视频可播放及不超过两分钟（有 ffprobe 时自动检查时长）。
10. 上传后重新下载或查看提交结果，以最后一次有效提交为准。
